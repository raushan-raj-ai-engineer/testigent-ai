# v1.10.2 Unified Test Creation

## Product rule

A user should not have to choose a separate command for normal UI versus complex UI. TestigentAI uses one authoring entry point and automatically records the component context required for dynamic tables/grids, nested iframes, open Shadow DOM, popups, dialogs, drag/drop, keyboard, file uploads, scroll/infinite scroll and network correlation.

## One user-facing command

```bash
npm run qa -- create <requirement-source> [authoring options]
```

Supported requirement sources include project Markdown and Jira (`JIRA:KEY` or a Jira `/browse/KEY` URL). The existing source adapter also continues to support the other normalized requirement sources already available in the framework.

### 1. Generate from existing approved knowledge

```bash
npm run qa -- create projects/ecommerce/requirements/create-order.md
npm run qa -- create JIRA:PAY-142
```

If an approved human-guided journey matches the requirement, the high-fidelity exploration renderer is used. Otherwise the framework falls back to requirement + approved application-knowledge scaffolding. The user does not choose a "complex" renderer.

### 2. Auto-explore and generate

```bash
npm run qa -- create JIRA:PAY-142 --auto-explore
```

The same process safely explores the selected application, captures reviewable page/API/navigation knowledge, asks for human knowledge approval in an interactive terminal, normalizes the requirement, and creates the proposal.

Safe auto-explore deliberately avoids destructive controls. Because a crawler cannot infer every business intent, generation may remain a review-gated scaffold when no approved event journey exists.

### 3. Manual journey learning and generation

```bash
npm run qa -- create JIRA:PAY-142 --learn="Create Order Journey"
```

One process opens the headed application. The tester performs the business journey and presses ENTER when complete. The recorder automatically captures semantic element identity plus component/frame/network context. Complex widgets do not require another mode.

Captured knowledge remains `REVIEW_REQUIRED` until the user approves it. In an interactive terminal the unified command shows the captured records and asks whether to approve them for generation.

### 4. One interactive command through promotion

```bash
npm run qa -- create JIRA:PAY-142 \
  --learn="Create Order Journey" \
  --reviewer="QA Lead" \
  --review-and-promote
```

The command performs:

```text
Requirement source
  -> optional auto explore OR manual learn
  -> knowledge review/approval
  -> source normalization (Markdown/Jira)
  -> proposal generation
  -> proposal validation
  -> pause for human editing when placeholders remain
  -> revalidation
  -> explicit approval prompt
  -> immutable approval hashes
  -> explicit promotion prompt
  -> active project automation
```

Human approval is never silently inferred. `--review-and-promote` is interactive and asks before approval and again before promotion.

## Complex UI is automatic

The guided capture layer detects and records, in the same workflow:

- HTML tables and ARIA grids
- AG Grid, MUI DataGrid, PrimeNG, Kendo and DevExtreme metadata
- stable row keys and virtualized-grid context
- nested iframe chains, including explicitly allowed cross-origin frames
- open Shadow DOM host metadata
- HTML/native dialogs
- popups/new tabs and downloads
- file-upload semantics without persisting sensitive local values
- keyboard actions and shortcuts
- native and pointer-inferred drag/drop
- hover
- scroll and near-bottom/infinite-scroll signals
- canvas click coordinates
- XHR/fetch traffic correlated to nearby UI actions

Generated grid automation prefers semantic row targeting instead of nth-child selectors. Generated iframe automation preserves frame context with `frameLocator()` chains.

## Requirement source flexibility

### Markdown

```bash
npm run qa -- create projects/ecommerce/requirements/payment.md
```

### Jira

```bash
npm run qa -- create JIRA:PAY-142
npm run qa -- create https://company.atlassian.net/browse/PAY-142
```

Jira authentication remains environment/config driven. Jira summary, description, labels, priority, components and configured acceptance-criteria/manual-step fields normalize into the same `RequirementDocument` used by local files.

## Compatibility

These commands remain supported so existing automation and CI do not break:

```text
qa:new
qa -- explore
qa -- learn
qa -- generate
```

They now route into the same unified `qa create` workflow. They are compatibility aliases, not separate product modes.

Low-level knowledge/proposal commands remain available for diagnostics and CI administration but are not required for the normal authoring journey.

## Internal regression policy

There is no dedicated user-facing `complex` command and no dedicated `test:complex-exploration` release command. The complex-widget contract lives in `tests/framework/unified-exploration-generation-contract.spec.ts` and is executed by the normal `test:framework:critical` regression suite.

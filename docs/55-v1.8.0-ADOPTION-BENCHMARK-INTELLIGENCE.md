# TestigentAI v1.8.0 — Adoption & Benchmark Intelligence

**Development candidate.** The immutable certified baseline is `v1.7.0` at commit `d9a228bc826e2bfaf4036535b61593ca25dad4b4`.

## Why this exists

The architect review did not ask for another feature checklist. It asked TestigentAI to prove adoption and differentiation with owned evidence: representative applications, multiple engineers, versioned datasets, raw results, explicit methodology and a plain-Playwright baseline. v1.8.0 turns that requirement into executable framework capability.

## Pilot evidence model

Project-owned observations remain under:

```text
.report-history/<application>/<environment>/adoption/observations/*.json
```

Portfolio reporting aggregates those immutable observations across applications for the selected environment. A pilot is `PILOT_EVIDENCE_READY` only after evidence includes at least:

- two representative applications;
- two opaque contributor aliases such as `engineer-1` and `engineer-2`;
- baseline-backed measurements before any comparative metric may be labelled improved/regressed.

Contributor keys deliberately reject email/name-like values. TestigentAI does not need employee PII to measure engineering adoption.

### Supported pilot metrics

- authoring session minutes;
- time to first passing test;
- requirement-to-approved-test minutes;
- migration minutes;
- triage minutes;
- CI wall time;
- CI cost;
- AI cost;
- report completeness;
- clean-pass rate;
- retry-pass rate;
- false-heal rate.

### Commands

```bash
APP=demo ENV=qa npm run qa:adoption -- record \
  --metric=triage-minutes \
  --value=8 \
  --baseline=20 \
  --contributor=engineer-1 \
  --evidence=reports/raw-triage-evidence.json

APP=demo ENV=qa npm run adoption:import-authoring -- \
  --contributor=engineer-1

APP=demo ENV=qa npm run qa:adoption -- report
```

The resulting dashboard page is `adoption-intelligence.html`.

## Comparative benchmark model

Comparative data is stored immutably under:

```text
.report-history/benchmark-intelligence/comparative/*.json
```

A metric can become `EVIDENCE_READY` only when it has repeatable baseline-backed samples across at least two applications. The analyzer rejects synthetic evidence for differentiation claims.

Every stored benchmark sample includes provenance sufficient to review the claim:

- TestigentAI version;
- source commit;
- Node runtime;
- OS/platform;
- runner/hardware/cloud description;
- dataset version;
- methodology;
- raw evidence reference;
- SHA-256 of the imported benchmark dataset;
- exclusions, if any.

Use the schema and non-executable template:

```text
schemas/testigent-benchmark-samples.schema.json
benchmarks/examples/comparative-benchmark.template.json
```

Copy the template, replace every placeholder, and then run:

```bash
npm run benchmark:compare -- \
  --input=benchmarks/my-pilot-comparison.json
```

The template itself has `templateOnly: true` and the CLI refuses to ingest it as evidence.

## False-heal benchmark

`evaluateFalseHealSafety()` measures injected business failures separately from successful locator recovery. Any injected business failure that becomes `CLEAN_PASS`, `HEALED_PASS` or `RETRY_PASS` is a false heal. The acceptance boundary is explicit: genuine business defects must not silently become green automation.

Persist measured seeded-defect evidence with:

```bash
npm run qa:false-heal -- --input=benchmarks/my-false-heal-run.json
```

Start from `benchmarks/examples/false-heal-evidence.template.json` and validate input shape against `schemas/testigent-false-heal-evidence.schema.json`. Template/synthetic evidence is non-certifying. The persisted record carries product version, commit, runtime/platform, environment, methodology, evidence reference and SHA-256 provenance and is rendered in `benchmark-intelligence.html`.

Comparative benchmark groups are kept separate by **dataset version + baseline label + metric**, so unrelated experiments cannot be merged into one differentiation claim.

## Reporting truth boundary

The business dashboard links to `adoption-intelligence.html` and `benchmark-intelligence.html`. Empty or sparse data renders `INSUFFICIENT_EVIDENCE`; TestigentAI never substitutes estimated savings or marketing assumptions for measured results.

# TestigentAI v1.4.2 — Senior Architect and Product Owner Review

Review date: 12 September 2026. Input: `testigent-ai-v1.4.2-FINAL(1).zip`.

## Decision

The direction aligns with current automation tooling: reusable Playwright infrastructure, AI-assisted authoring, governed recovery, and actionable reporting. The implementation is a credible internal quality-engineering accelerator. Broad enterprise readiness and commercial product-market fit are not established by this archive.

Continue development. Approve a controlled pilot with synthetic data and named maintainers after the high-priority defects below are resolved. Do not yet approve unrestricted use of sensitive evidence with AI providers or concurrent executions in a shared checkout.

This is a source and targeted execution review, not a penetration test, exhaustive audit, or certification. No source fixes were applied to the submitted release.

## Strengths worth preserving

1. **Explicit ownership:** reusable capability lives in `src/framework`; application routes, selectors, workflows and repositories live in `projects/<project>`. Boundary checks support the intended architecture.
2. **Recovery intent:** the healer prioritizes primary locators, declared fallbacks, validated cache, then optional AI. Ambiguity checks and semantic post-conditions are meaningful protections.
3. **Authentication lifecycle:** project-owned providers, refresh locking, fresh-context verification and navigation-only recovery are thoughtful design choices. Live behavior still needs validation.
4. **Reporting semantics:** clean pass, healed pass, retry pass, known defect and unexpected pass are distinguished. Known defects remain quality failures even when accepted by the runner. Merge topology checks protect against missing worker bundles.
5. **Proposal governance:** approval records and approved file hashes prevent accidental promotion of changed generated files. This is useful workflow integrity; authenticated enterprise authorization is a separate requirement.
6. **Test-data identity:** run, application, environment, test, case and attempt participate in generated data identities. This is a sound basis for parallel execution.
7. **Operational investment:** pinned dependencies, CLI entry points, project templates, quality lanes, framework tests and extensive documentation show substantive implementation beyond a README.

## Architect findings, ordered by priority

### A1 — High: sensitive data survives redaction

Evidence: `src/framework/logging/redactor.ts`, `src/framework/api/base-api.client.ts`, `src/framework/ai/ai.gateway.ts`.

The shared redactor masks values according to object key names but leaves string contents untouched. The API client converts a response to text and places it in `responseBody`. Healing passes a string in `accessibilitySnapshot`. Embedded JSON credentials, free-text personal data and query-string secrets can survive. A synthetic probe confirmed this boundary defect; it did not demonstrate any actual user-data disclosure.

Correction: parse and recursively redact JSON before truncation; sanitize URLs; use explicit evidence-field allowlists and a configurable free-text sanitizer. Treat screenshots, videos and traces as separate sensitive artifacts requiring capture and retention policy.

Acceptance: synthetic canary secrets in JSON, URL queries, plain text and snapshots are absent from persisted evidence and mocked outbound AI payloads. Sensitive visual regions have an explicit masking/exclusion policy.

### A2 — High: cloud egress controls rely on provider labels

Evidence: `src/framework/ai/ai-provider.factory.ts`, `http-ai.provider.ts`, `openai-compatible.provider.ts`, `ollama-ai.provider.ts`.

Only OpenAI, Anthropic, Azure OpenAI and Gemini names are classified as cloud providers. Generic HTTP, OpenAI-compatible and configurable Ollama endpoints can point outside the organization without that permission check. The configuration probe accepted an external HTTP-provider URL with `AI_ALLOW_CLOUD_EGRESS=false`.

Correction: enforce the resolved destination's origin and transport policy for every adapter. Configure explicit approved private/local origins and external origins; enforce policy across redirects. Do not infer locality from the adapter name.

Acceptance: all adapters reject unapproved external destinations before network activity; approved private gateways remain usable.

### A3 — High: automatic browser dependency in API/data/DB fixtures

Evidence: `src/framework/core/fixtures/enterprise.fixture.ts`, particularly `_authStateBootstrap`.

The automatic fixture requests `context`, which initializes a browser even if the test uses only API or data capabilities and authentication strategy is none. API-tagged data contract tests failed on the missing browser prerequisite during this review.

Correction: separate a browser-free base fixture from UI/E2E extensions. Move session-storage bootstrap into the UI context fixture. Keep API and DB evidence available without browser startup.

Acceptance: API-only, data-only and DB-only suites run on a worker with no browser binaries installed. UI/E2E suites retain authenticated context behavior and screenshots.

### A4 — High for concurrent shared-checkout use: run isolation is incomplete

Evidence: `src/framework/core/setup/global.setup.ts`, `core/config/run.context.ts`, `core/config/runtime.config.ts`, `scripts/test-project.ts`.

All runs write `.runtime/run-context.json`; readers prefer this file over `RUN_ID`. Reports and test results are scoped by application, and the runner deletes that application's business report directory before execution. Two processes sharing a checkout can overwrite run identity; concurrent environments of the same application can collide on outputs.

Correction: immutable per-process run identity propagated to workers; artifact paths scoped by application/environment/run ID. Keep a separate latest-run pointer for user convenience. Clean only the current run's directory.

Acceptance: execute two runs for the same application in QA and UAT concurrently from one checkout. Each report, log, attachment and test-data identity retains its own provenance. Isolated CI workspaces reduce exposure but do not fix the local/shared-runner case.

### A5 — Medium: healing cache lacks environment scope and concurrent write safety

Evidence: `src/framework/healing/healing.cache.ts`.

The default cache is application-scoped and keyed by plan ID. Whole-file read/modify/write operations have no locking or atomic publication. Environment differences and concurrent writers can cause inappropriate reuse or lost entries; malformed JSON is silently treated as an empty cache. This is a source-identified risk, not a measured concurrency incident.

Correction: include environment and locator-plan/application revision in cache provenance, add expiry/invalidation policy, and use atomic writes plus a lock or suitable transactional store. Retain semantic validation on reuse.

Acceptance: concurrent writes preserve all entries; QA entries do not silently become UAT candidates; stale or incompatible entries are rejected with diagnostics.

### A6 — Medium: locator probing can bypass Playwright's waiting behavior

Evidence: `src/framework/healing/healing.orchestrator.ts`, `usableLocator()`.

The function calls `visible.count()` first and immediately rejects zero matches. Its later `waitFor()` is never reached for an element that appears shortly afterwards. A normal rendering delay can trigger fallback/AI or failure. This path is confirmed in source; a browser timing reproduction remains pending.

Correction: give the primary locator a bounded readiness window before recovery; recheck visible uniqueness after waiting. Make timeout and recovery reasons explicit in evidence.

Acceptance: delayed primary controls succeed without invoking AI; multiple visible matches still fail safely; legitimately removed locators enter recovery.

### A7 — Medium: generic HTTP AI adapter differs from provider reliability policy

Evidence: `src/framework/ai/http-ai.provider.ts`, compared with `ai-provider.utils.ts`.

The generic adapter uses raw fetch without an explicit application timeout and casts JSON to the expected type. Non-OK responses return undefined, reducing error diagnostics. Other providers use shared timeout/parser mechanisms.

Correction: apply bounded timeout, cancellation, schema validation and categorized errors consistently. Define retry policy explicitly and count attempts against usage limits.

Acceptance: stalled, malformed, throttled and unavailable responses terminate within policy and produce redacted, actionable diagnostics.

### A8 — Medium: security exception is too broad for future advisories

Evidence: `scripts/security-check.ts`.

Any high/critical finding named xlsx is allowlisted when the installed version is 0.20.3. A new advisory affecting that version would inherit the exception. The current audit returned zero high/critical findings; this is a policy defect, not a claim that the shipped package is currently vulnerable.

Correction: scope exceptions by advisory ID, affected range, rationale, owner and expiry. Fail when an advisory is not explicitly covered. Use validated SBOM tooling and artifact provenance as enterprise distribution matures.

Acceptance: an injected new advisory for the same package/version blocks the gate while a specifically approved exception is reported visibly.

## Product owner assessment

### Market relevance and differentiation

The capability direction is current, but a checklist does not prove customer demand. Playwright itself provides planner, generator and healer agents; the official MCP server is also available. Commercial tools such as Testim advertise AI authoring, self-healing and quality intelligence. These primary product sources demonstrate competitive overlap, not independent proof of effectiveness or willingness to pay. [Playwright agents](https://playwright.dev/docs/test-agents), [Playwright MCP](https://github.com/microsoft/playwright-mcp), [Testim](https://www.testim.io/).

The strongest proposed differentiator is: **one team-owned automation core across applications, with controlled AI assistance and trustworthy release evidence**. Validate that proposition with platform/QE leads maintaining several web applications and existing Playwright suites. Do not initially target every testing discipline or a full device-cloud replacement.

### Claim maturity

| Capability | What this release supports | What should remain qualified |
| --- | --- | --- |
| UI/API/DB | Real infrastructure, project boundaries and adapters | Live database correctness and end-to-end portability were not exercised |
| Business reporting | Substantial semantics and passing merge contracts | Interactive browser/PDF behavior was not verified on this host |
| Self-healing | Deterministic recovery plus optional AI and semantic checks | No measured false-heal rate or comparative maintenance savings |
| Accessibility | Basic DOM smoke checks | Not a comprehensive accessibility audit; integrate a dedicated engine and manual assessment |
| Performance | Navigation/resource timing budgets | Not concurrency/load/soak testing or a complete Web Vitals program |
| AI application evaluation | Provider-neutral runner and deterministic output/fact metrics | No demonstrated calibrated RAG, hallucination or agent-task evaluation suite |
| Governance | Local review state, audit events and approved hashes | Not authenticated RBAC or a tamper-resistant multi-tenant control plane |
| Scale | Sharding/configuration infrastructure and planning utilities | No demonstrated 500/2,000-test scaling benchmark in this review |

The accessibility source is candid about its limited scope. Preserve that distinction in product messaging. Playwright documents axe integration and the need for manual testing alongside automation. [Playwright accessibility guidance](https://playwright.dev/docs/accessibility-testing).

### Adoption priorities

Promote the existing `qa` CLI as the primary user journey: select project, doctor, run, inspect evidence. Expose advanced commands progressively. Add a migration path for existing Playwright tests so adoption does not require an immediate rewrite into every framework layer.

Keep the current modular repository while proving adoption. A stable versioned core package can follow when multiple teams need independent upgrades; it does not require microservices. For a hosted multi-user product, authenticated permissions, durable evidence storage, tenant isolation and service operations become additional requirements. For an internal repository, protected Git reviews and CI ownership can provide much of the approval boundary.

Do not add accessibility, performance or AI evaluation adapters simply to expand the feature list. Prioritize them when a pilot needs them. API schema/contract validation is a useful candidate for service-heavy teams; evaluate it against actual customer scenarios.

## Recommended next release backlog

| Sequence | Deliverable | Completion evidence |
| --- | --- | --- |
| 1 — Trust and correctness | A1–A4, with focused regression tests | Sanitization/egress probes blocked correctly; browser-free API lane; isolated simultaneous runs |
| 2 — Recovery reliability | A5–A8 | Cache concurrency tests, delayed-locator test, provider timeout/error tests, advisory-scoped exceptions |
| 3 — Reproducible release | Run supported Node/OS/browser matrix and real CI pipelines | Exact dependency/browser versions, full results, report artifacts and documented exclusions |
| 4 — Pilot adoption | Two representative applications and at least two engineers | Recorded onboarding and authoring time, migration friction, support burden |
| 5 — Evidence-based differentiation | Execute the existing competitive benchmark plan | Versioned datasets, raw results, methodology and plain-Playwright baseline |

Proposed pilot metrics, to be agreed before measurement: time to first passing UI/API test; median requirement-to-approved-test time; clean-pass and retry-pass rates; false-heal rate on injected defects; triage time; report completeness; CI wall time and cost; AI usage/cost. Targets are product decisions, not observed achievements.

For safety-sensitive operations, the seeded-defect acceptance criterion should be that no genuine business failure is silently converted into a clean pass. Measure this separately from successful locator recovery.

The archive already contains `docs/22-COMPETITIVE-BENCHMARK-PLAN.md`, covering authoring, scale, data safety, false healing, RCA and portability. Execute that plan and publish evidence before adding another market-readiness document.

## Suggested positioning

**TestigentAI — Governed Quality Engineering for Multi-Application Teams**

A reusable Playwright and TypeScript foundation for UI, API and database testing, with AI-assisted authoring, controlled locator recovery and business-readable release evidence.

This wording focuses on the product's strongest implemented direction. Keep broader accessibility, performance and AI-application evaluation claims at their demonstrated maturity levels.

## Final recommendation

Retain the architecture and narrow the next release to reliability, data protection and adoption evidence. The product is relevant and promising as an internal QE accelerator. Enterprise-wide rollout should wait for the high-priority corrections and complete integration validation. Commercial readiness requires customer evidence in addition to engineering gates.
